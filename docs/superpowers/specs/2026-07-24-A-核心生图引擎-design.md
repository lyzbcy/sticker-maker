## 0. 上下文与定位

### 0.1 项目全景（5 个子项目）

《初心与使命》要"把表情包制作流程打包成软件分发给粉丝"，整体太大无法塞进单个 spec，已拆成 5 个子项目，各自独立走 spec → 计划 → 实现：

| 子项目 | 职责 | 依赖 |
|---|---|---|
| **A. 核心生图引擎（本文）** | 跨平台 Python 核心库：生图/抠图/裁切/素材生成 | —（地基） |
| B. Mac 应用外壳 | GUI、首次向导、`.app` 打包、内存日志 | A |
| C. 发布与上架 | 跨平台发布流、一键多平台、自动上架 | A |
| D. AI Agent 接口 | 外部 agent 控制接口、定时发布、省 token 复用 | A |
| E. 推广系统 | 表情包推广、三码（赞赏/入群/表情包） | A |

**A 是地基**，B/C/D 全部通过 A 的 API 调用。A 做不好，上层全是空中楼阁。

### 0.2 A 的交付边界

- **交付**：一个可移植的 Python 核心库 `sticker_engine`，含清晰 API。
- **不交付**：GUI（B）、发布能力（C）、agent 接口（D）、推广（E）。
- **验证方式**：单元测试 + CLI 冒烟测试（B 出来前靠 CLI 验证端到端）。

## 2. 架构总览

### 2.1 分层

```
                      ┌─────────────────────────────────────┐
   上层(B GUI/C/D) ──→ │  api.py  StickerEngine              │
                      │   .configure(cfg) / .run(progress_cb)│
                      └──────────────┬──────────────────────┘
                                     │
                      ┌──────────────▼──────────────────────┐
                      │  pipeline/runner.py                 │
                      │   顺序跑 Stage，关卡门禁，进度回调   │
                      └──────────────┬──────────────────────┘
                                     │ 传递 PipelineContext
          ┌──────────────┬───────────┼───────────┬──────────────┐
          ▼              ▼           ▼           ▼              ▼
     stages/prep   stages/generate  │    stages/postprocess  stages/assets
                                    │
                              (关卡 validate 嵌在阶段之间)
                                    │
          ┌─────────────────────────┴────────────────────────┐
          ▼                ▼                ▼                 ▼
   providers/codex   providers/chromakey  providers/vision  config/
   (CLI调用+捞图)    (内置Pillow抠图)     (含义预检识图)     (角色/概率/路径)
                                    │
                      ┌─────────────▼──────────────┐
                      │  resources/  (内置只读资产) │
                      │   base图×4角色、174剧本、   │
                      │   关键词库、prompt模板      │
                      └────────────────────────────┘
```

### 2.2 五条核心设计原则（从现有 skill 血泪经验提炼）

1. **关卡门禁是一等公民** —— `validate` 嵌在阶段之间作为 `Gate` 对象。FAIL 必停，不许跳步。对应现有 `<creator-hard-rules>`"宁可停在当前关卡报错，也不要跳步"。
2. **生产日志内建** —— 每个 Stage 执行完往 `PipelineContext.production_log` 追加一条。7 个必经步骤（准备/生图/含义预检/透明化/最终版/发布素材/校验）的完成状态 run 结束后可查。
3. **providers 依赖反转** —— codex/抠图/识图这些"外部世界"全走 provider 接口，核心逻辑不直接 `subprocess`。B 能注入 mock provider 做 GUI 预览，D 能替换 provider 接别的 AI。
4. **resources 只读** —— 内置 base 图/剧本库/关键词库是只读资产，用户配置和产出写到独立 user-data 目录，两层不混。
5. **配置驱动，无硬编码路径** —— 所有路径来自 `Config`，不存在 `E:\` 或 `~/` 字面量散落。

### 2.3 对外 API

```python
from sticker_engine import StickerEngine, Config, Paths

config = Config.load_default().with_paths(Paths.resolve())
config.prefs.mode_probs = ModeProbs(single=0.5, duo=0.3, trio=0.0, quad=0.2)

episode = engine.run(
    progress_callback=lambda ev: gui.update_progressbar(ev),

# episode.episode_dir / episode.stickers / episode.meaning_map / episode.assets / episode.production_log
```

## 3. 阶段与数据模型

### 3.1 四个 Stage + 三道关卡

| Stage | 输入 | 产出 | 关键逻辑（移植自现有脚本） |
|---|---|---|---|
| **S0 Prep** | Config | `EpisodeDir`（标准目录 + `prep_state.json` + `本次制作角色.md`） | 按概率选模式（单/双/三人/四人）→ 按概率选角色 → 按概率选 base 图 → 复制参考图（若走参考图库模式）。**可选**：调 `providers/codex.generate_base_image(prompt)` 生成新 base（J1） |
| **→ Gate0** `pre_generate` | EpisodeDir | PASS/FAIL | base 图存在、参考图库可读、**codex 可调用**（A1 检测点：返回 `CodexStatus`，`image_ready=False` 即 FAIL 并附 `guidance_msg`） |
| **S1 Generate** | EpisodeDir | `GridImage`（存 `原图/grid_{N}x{N}.png`） | 三模式分派（见 3.2）→ 拼 prompt → 调 `providers/codex.generate_grid()` → 从 codex 输出目录捞最新图 |
| **→ Gate1** `post_generate_raw` | GridImage | PASS/FAIL | 图存在、非空、尺寸合理、宫格没塌 |
| **S2 Postprocess** | GridImage | `StickerPack`（透明 PNG + `meaning_map.json`） | 裁切 → 含义预检（`providers/vision`）→ **条件抠图**（见 3.3）→ 按含义词重命名 → 写 `最终版/` |
| **→ Gate2** `post_generate` | StickerPack | PASS/FAIL | 数量符合 grid（1/4/9/16）、尺寸 240-360、RGBA、含义词无重复 |
| **S3 Assets** | StickerPack | `Assets`（横幅750×400 / 封面240×240 / 图标50×50 / `介绍.txt`） | 选最佳图 → 合成横幅 → 单角色特写做封面/图标 → AI 撰写 1-80 字介绍 |

> **A 不含发布**（S3 只产素材）。发布归 C 子项目。A 的产出定义：**一弹可在微信平台发布的完整素材**。

### 3.2 生图三模式（S1 分派器）

```
S1 Generate 收到 EpisodeDir
  ├─ 模式判定优先级：
  │   if config.prefs.ref_lib_priority AND 参考图库可用图 ≥ grid_count:
  │       → 参考图库模式
  │   elif config.prefs.story_mode:
  │       → 故事模式
  │   else:
  │       → 提示词排列组合模式
  │
  ├─ 参考图库模式：image1=base, image2..N=参考图 → 单次 N×N
  ├─ 故事模式：story/ 引擎选 N 组剧本 → 拼 prompt → 单次 N×N
  └─ 排列组合模式：keywords 按类型随机挑（姿势×表情）→ 拼 prompt → 单次 N×N
```

三模式共用同一条 codex 调用路径（`providers/codex.generate_grid(prompt, refs, grid_size)`），仅 prompt 构造不同。

### 3.3 S2 抠图条件矩阵（修正版，对应《初心与使命》第 47-52 行）

| 生图模式 | 默认背景 | 默认是否抠图 |
|---|---|---|
| 参考图库模式 | 保留参考图原有背景 | **否**（除非用户勾选 `transparent_background`）。"保留背景"= 完全跳过抠图，直接用 codex 生成结果（参考图是什么底就是什么底） |
| prompt 模式（故事/排列组合） | 洋红 #ff00ff | **是** |
| 1×1 生图 | —— | **不切图**（单张即成品，跳过裁切） |

S2 行为由 `EpisodeSpec` 的两个开关驱动：`transparent_background` 和 `grid_size`。
当 `grid_size == 1` 时跳过裁切；当模式为参考图库且 `transparent_background=False` 时跳过抠图。

### 3.4 生图资源消耗（grid_size 可选）

默认 4×4。支持用户选 3×3 / 2×2 / 1×1（对应《初心与使命》第 55-58 行）。grid_size 影响：
- 参考图库模式的最低可用图数（4×4 需 ≥16 张）
- 故事模式的剧本组数（4×4 = 4 组 × 4 panel）
- S2 是否切图（1×1 不切）

### 3.5 核心数据模型

```python
@dataclass
class PipelineContext:
    config: Config
    episode: EpisodeSpec          # 本次意图：模式概率、指定角色、grid_size、透明开关
    episode_dir: Path
    grid_image: Path | None       # S1 产出
    stickers: list[Sticker]       # S2 产出（path / meaning / panel_index）
    meaning_map: dict[int, str]   # 故事线顺序（发布时按 1→N 上传）
    assets: Assets | None         # S3 产出
    production_log: list[LogEntry]  # 内存日志（环形缓冲，容量 50）
    errors: list[GateError]       # 关卡失败记录

@dataclass
class ProgressEvent:
    stage: str          # "S0"/"S1"/"S2"/"S3"
    phase: str          # "calling_codex"/"scanning_output"/"chromakey"/...
    message: str        # 中文，给用户看
    percent: float      # 0.0-1.0
    eta_seconds: int | None  # 基于历史耗时滑动平均
```

## 4. 配置层 + 资源 + 跨平台路径

### 4.1 配置三层分离

```python
@dataclass
class Config:
    # 第 1 层：内置默认（只读，随包分发）— resources/default_config.yaml
    characters: dict[str, Character]   # 4 角色 + base 图 + 默认概率
    story_library: LinkageLibrary      # 174 组剧本
    keywords: Keywords                 # 情绪/动作/背景
    magenta_key: str = "#ff00ff"
    green_key: str = "#00ff00"

    # 第 2 层：用户偏好（持久化）— user_data/prefs.yaml = "前情提要"
    prefs: Prefs

    # 第 3 层：环境路径（运行时解析，不持久化为字面量）
    paths: Paths
```

**第 2 层 prefs 就是"前情提要"**（对应《初心与使命》第 27 行）。首次启动向导（B）填它；之后每次 run 默认读它跳过向导；用户想改随时进设置改。

```python
@dataclass
class Prefs:
    mode_probs: ModeProbs              # 单/双/三人/四人概率（和=1.0）
    single_char_probs: dict[str,float] # 单人模式各角色概率
    base_probs: dict[str,dict[str,float]]  # 每角色多 base 概率（和=1.0）
    grid_size: int = 4
    transparent_default: bool = True   # prompt 模式默认透明
    ref_lib_priority: bool = True      # 参考图库优先
    story_mode: bool = True            # prompt 模式默认故事
```

### 4.2 内置资产 resources/

```
resources/
├── default_config.yaml        # 4 角色 + base 概率（移植自现有 config.yaml）
├── base_images/               # 4 角色 base 图（≈16MB）
│   ├── 星星布丁/{base1,3,4,5,6}
│   ├── 捞鱼/{base1,2,3,4}
│   ├── 周三涵/{base1,2}
│   └── 周五涵/base1
```

分发方式：打进 Python 包的 `package_data`（`pip install` 一起落地），非外部目录。

### 4.3 跨平台路径（Mac 先行，Win 预留）

```python
@dataclass
class Paths:
    user_data: Path    # Mac: ~/Library/Application Support/StickerEngine/
                       # Win: %APPDATA%/StickerEngine/
    output_root: Path  # 默认 = user_data/episodes/，用户可改
    reference_lib: Path # 默认 = user_data/reference_library/，不存在自动创建
    prefs_file: Path   # = user_data/prefs.yaml
    codex_exec: str    # "codex"（PATH 找）或用户指定路径
    codex_output_dir: Path  # Mac: ~/.codex/generated_images/
                            # Win: %USERPROFILE%\.codex\generated_images\
```

所有平台差异收拢在 `Paths.resolve(platform)` 一个函数（内部用 Python 标准库 `os.path.expanduser` / `appdirs` 解析 OS 标准位置，**不写死任何字面量路径**）。移植 Win 时只改这函数 + 打包脚本，核心逻辑零改动。

### 4.4 codex 检测（A1）

```python
@dataclass
class CodexStatus:
    installed: bool
    logged_in: bool
    image_ready: bool
    guidance_msg: str   # 失败时给用户看的引导文案

class CodexProvider:
    def check(self) -> CodexStatus: ...
```

A 只负责"检测+报告"；"怎么引导用户装 codex"留给 B（GUI 的事）。`check()` 返回 `image_ready=False` 时，`run()` 在 Gate0 即 FAIL 并附 `guidance_msg`。

### 4.5 AI 能力的 codex 复用（决策 K 落地）

生图之外，A 还需要两类 AI 能力：**含义预检（识图命名）** 和 **介绍文案撰写**。两者都复用 codex exec（决策 K），用户零额外配置。

| AI 能力 | 所在 Provider | codex 调用方式 | 性能优化 |
|---|---|---|---|
| 生图 | `CodexProvider.generate_grid()` | `codex exec --enable image_generation` | 单次 N×N |
| 含义预检 | `VisionProvider.interpret()` | `codex exec`（带图，问"这 16 个表情各是什么含义"） | **16 张拼 1 张大图，1 次调用**（移植现有 `check_and_rename.py` 的拼图优化） |
| 介绍文案 | `VisionProvider.write_intro()` | `codex exec`（带含义词列表，要求 1-80 字） | 1 次调用 |

> `VisionProvider` 名字保留（语义清晰），但**实现内部就是调 codex**，不是独立 AI 服务。这样架构上 provider 抽象不破，未来 D 子项目要接别的 AI 时只需替换 `VisionProvider` 实现。

**S1 模式判定与剧本池降级（决策 L 落地）**：故事模式下 `story/selector` 若发现可用剧本 < N 组（grid_size=4 时需 4 组），自动降级到排列组合模式，并在 `production_log` 和进度事件里记 WARN（"剧本池不足，已降级到排列组合模式"）。174 组 ÷ 每次 4 组 ≈ 43 弹才会耗尽，正常用户基本触达不到；触达时降级保证流程不中断。

## 5. 测试策略 + 已知边界 + 风险（第 4 段）

### 5.1 测试策略

| 层 | 方式 | 覆盖 |
|---|---|---|
| **providers** | 单元测试 + mock | `CodexProvider`（mock subprocess + 扫输出目录）、`ChromaKeyProvider`（用现有"原图_透明ChromaKey"素材做 A/B 对齐）、`VisionProvider`（mock） |
| **stages** | 单元测试，注入 mock providers | 每个阶段独立测，关卡门禁的 PASS/FAIL 分支都要覆盖 |
| **pipeline** | 集成测试，全 mock provider | 端到端跑通 S0→S3，验证生产日志 7 步齐全、进度事件序列正确、stop_event 能中断 |
| **story 引擎** | 单元测试 | 剧本选取（角色严格匹配）、已用淘汰、N 组串联、池子不足降级 |
| **config/paths** | 跨平台测试 | Mac/Win 路径解析、prefs 持久化往返 |
| **CLI 冒烟** | 真实 codex（手动） | 不进 CI（依赖真实 codex 登录），作为发布前手动验证 |

**抠图对齐验证（关键）**：重写的 `ChromaKeyProvider` 必须用你现成的"原图_透明ChromaKey"素材（弹次目录里有大量样本）做像素级 A/B 对比，确保 hue-guard 红衣保护、soft-matte、edge-contract 全部不退化。这个测试是 A 子项目的验收红线之一。

### 5.2 已知边界（A 不做的事）

- **不含 GUI** —— B 负责。A 提供 CLI 仅用于冒烟测试。
- **不含发布** —— C 负责。S3 产出"可发布的素材"，但不提交到微信。
- **不含 codex 安装引导 UI** —— A 的 `CodexProvider.check()` 只返回状态和文案，不执行安装。
- **不内置参考图库** —— 用户自建（C 决策）。
- **不实现"多平台发布"** —— 当前只考虑微信规范（240×240 等），别的平台等 C。
- **动态表情（GIF）暂不在 A 的主线** —— 现有 skill 有 `make_gif.py`/`batch_dynamic.py`，但《初心与使命》主线讲的是静态。A 的架构预留 `grid_size` 和帧图扩展位，但实现优先静态。

### 5.3 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| **codex CLI 输出目录结构变更**（`~/.codex/generated_images/` 路径或命名变） | 高 | `CodexProvider` 集中封装捞图逻辑，路径做成可配置 + 多候选探测；CI 用 mock，真实变更时手动冒烟能快速发现 |
| **抠图重写效果退化** | 高 | 像素级 A/B 对齐测试（5.1）；保留"切回调 codex 自带脚本"的开关作为兜底（架构预留，默认不开） |
| **codex 登录态判断不准** | 中 | `check()` 不只看文件存在，试跑轻量命令验证；失败给清晰引导 |
| **联动剧本池耗尽**（174 组用完，≈43 弹） | 低 | 决策 L：自动降级到排列组合模式并 WARN，流程不中断（见 4.5） |
| **大 base 图导致包体积过大** | 低 | base 图合计 ≈16MB，可接受；必要时做压缩或按需下载 |
| **三模式 prompt 模板质量** | 中 | 移植现有 `reference/prompt-templates.md` 已验证的模板，不新造 |
