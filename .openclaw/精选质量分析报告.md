# 精选表情质量分析报告与 Skill 优化方案

> 分析日期：2026-07-06
> 数据样本：54 弹表情包（927 张成品），其中 138 张精选（精选率 14.9%）
> 数据来源：各弹 `prep_state.json` 制作参数 + 精选目录人工标注
> 目标：找出影响表情质量的正/负面因素，并据此优化 `lyzbcy-sticker-creator` skill

---

## 一、核心结论（先看这里）

| 影响因素 | 方向 | 强度 | 数据依据 |
|---------|------|------|---------|
| **单人模式 (single) 行** | ✅ 强正面 | ★★★★★ | single 平均精选率 22.5% vs duo 8.5% |
| **参考图模式 (reference)** | ✅ 强正面 | ★★★★★ | reference 37.5% vs ai_template 10.2% |
| **整弹全双人 (duo)** | ❌ 强负面 | ★★★★★ | 33 弹 duo 中 22 弹（67%）精选率为 0% |
| **行级混入少量双人** | ⚠️ 中性偏正 | ★★★ | 第12弹(duo)81%、第53弹(duo)31% 证明双人能出彩 |
| **四人模式 (quad)** | ❌ 强负面 | ★★★★ | 唯一 1 弹 quad 精选率 0% |
| **口语化短含义命名** | ✅ 正面 | ★★★★ | 高质量弹均字 2.1 字 vs 低质量 2.7 字 |
| **base5/base4 服装** | ✅ 正面 | ★★★ | base5=22.7% / base4=15.4% vs base3=0% / base6=3.7% |
| **短词 emotion_action 组合** | ✅ 正面 | ★★★ | 高质量弹 100% 用此风格 |
| **参考图数量 14（偏多）** | ❌ 负面 | ★★ | refs=14 平均仅 5.7% 精选率 |

**一句话总结**：当前最大的质量黑洞是 **duo 双人模式**——它消耗了 33 弹资源，却贡献了最多的 0% 精选弹。但解法**不是一刀切全转 single**，而是采用 **「行级混合模式」**：每弹 4 行故事里，单人行为主（保精选率下限），双人行为辅（保题材多样性），让单人的稳定性 + 双人的互动性各取所长。

### 2.2 关键变量交叉分析

#### 发现 1：模式（mode）是最强质量分水岭

```
single 单人：平均 22.5% 精选率  (n=15弹，4弹≥30%)
duo   双人：平均  8.5% 精选率  (n=33弹，2弹≥30%) ← 67%的弹精选率为0
quad  四人：平均  0.0% 精选率  (n=1弹)
```

**duo 模式的问题本质**：双人互动场景在 240×240 小尺寸下，两个角色的表情/动作细节都被压缩，难以像单人那样做到「一眼就能看懂的情绪」。生图模型在处理双人构图时也更难保持角色一致性和动作清晰度。

#### 发现 2：reference 模式碾压 ai_template 模式

```
reference（用16张已有参考图做pose参考）   ：平均 37.5% (n=4弹)
ai_template_reviewed（AI审核过的提示词）   ：平均 12.3% (n=3弹)
ai_template（纯提示词组合）              ：平均 10.2% (n=42弹)
```

reference 模式质量高的原因：参考图本身就是「被验证过的优质表情pose」，生图只是换个角色重绘，相当于站在巨人肩膀上。而 ai_template 全靠提示词「想象」pose，质量方差极大。

#### 发现 3：高质量弹的 keyword 风格高度一致

全部 6 个高质量弹（100%）都使用 **短词 emotion_action 组合**（如 `laughing_launching`、`love_spinning`），而非长描述句（如 `hugging with shy smiles`）。

短词组合的优势：每个 panel 的情绪和动作都是明确的「原子单元」，AI 生图时不会因为描述过长而模糊焦点。

#### 发现 4：服装 base 的影响

```
base5: 平均 22.7% (n=14) ← 最佳
base4: 平均 15.4% (n=17)
base6: 平均  3.7% (n=10) ← 最差
base3: 平均  0.0% (n=6)  ← 全军覆没
```

base3/base6 服装的表现明显偏差。这可能与特定服装的角色辨识度、生图稳定性有关，建议复盘这两个 base 的实际素材质量。

#### 发现 5：含义命名的聊天实用度

高质量弹含义词（第9弹）：可怜、可恶、吃、哦、嘶、坏笑、天塌了、工作、无力、无语、灵机一动、皱眉、萌萌、诶、闪亮眼 —— **平均 2.1 字，几乎都是日常聊天高频反应词**。

低质量弹含义词（第14弹）：亲亲、冷战、哇哦、委屈、害羞低头、并肩坐、开心抱、悄悄话、惊讶对视、手拉手、捂嘴笑、欢呼、比心、甜蜜抱、躺一起、靠着你 —— **平均 2.7 字，多为「描述性场景词」，不是聊天会用的反应**。

> 微信表情的核心使用场景是「聊天回复」。一个叫「无语」的表情，远比一个叫「靠着你」的表情更容易被用户在对话中发送。

## 三、正面 / 负面因素清单

### ✅ 正面影响因素（向精选靠拢要做的）

| # | 因素 | 说明 | 证据 |
|---|------|------|------|
| 1 | **单人主角构图** | 240×240 尺寸下，单角色的表情细节最清晰 | single 精选率是 duo 的 2.6 倍 |
| 2 | **使用已有参考图** | reference 模式用验证过的 pose，质量下限有保障 | reference 37.5% vs ai_template 10.2% |
| 3 | **短词 emotion_action 组合** | `情绪_动作` 格式比长描述句更聚焦 | 6/6 高质量弹均用此格式 |
| 4 | **口语化聊天含义命名** | 命名要像「聊天会发的反应词」 | 高质量弹均字 2.1，低质量 2.7 |
| 5 | **base5 / base4 服装** | 这两套服装的角色表现最稳定 | base5=22.7%, base4=15.4% |
| 6 | **单一清晰情绪** | 每张表情只表达一个一眼能懂的情绪 | 高质量弹含义词多为单字/双字情绪 |
| 7 | **参考图数量适中（16）** | refs=16 时平均精选率 34.2% 最高 | 远超 refs=14 的 5.7% |

### ❌ 负面影响因素（要避免的）

| # | 因素 | 说明 | 证据 |
|---|------|------|------|
| 1 | **双人/多人互动场景** | 小图压缩+生图不稳定，表情难辨 | duo 67% 弹精选率为 0% |
| 2 | **纯提示词生图（无参考图）** | ai_template 模式质量方差大 | 42 弹平均仅 10.2% |
| 3 | **base3 / base6 服装** | 这两套服装表现差 | base3=0%, base6=3.7% |
| 4 | **描述性/剧情化含义命名** | 「靠着你」「并肩坐」等非聊天词 | 低质量弹命名特征 |
| 5 | **抽象/文学化情绪词** | floating/melting/starstruck 等 | 第7弹(纯捞鱼)0% 精选 |
| 6 | **参考图过多但质量参差（14张）** | refs=14 反而精选率最低 | 5.7%，可能稀释了优质参考 |
| 7 | **单人纯捞鱼角色** | 第7弹、第51弹均 0% | 捞鱼单独出镜效果差 |
| 8 | **长描述句 keyword** | "hugging with shy smiles" 类 | 焦点模糊，生图易跑偏 |

## 四、Skill 优化设计方案

基于以上分析，对 `E:\星星布丁\微信表情包\.openclaw\skills\lyzbcy-sticker-creator` 提出以下分层优化方案。

> **核心设计原则（来自用户反馈）**：不做"一刀切"。single 质量好，但不意味着整弹只用 single。
> 正确做法是**行级混合**——每弹 16 格 = 4 行故事，按概率给每一行独立分配模式，
> 让单人（稳精选率）与双人（保题材丰富）在同一弹里共存。

### 4.0 核心机制：行级混合模式（最重要的改动）

#### 问题回顾
当前 `prep_state.json` 在准备阶段就对整弹定一个 `mode`（single/duo/quad），导致：
- 定了 duo，整弹 16 格全是双人 → 命中 67% 的 0% 精选概率
- 定了 single，整弹 16 格全是单人 → 题材单一，缺少互动趣味

#### 新机制：4×4 的每一行独立选模式

```
16 宫格 = 4 行 × 4 格
当前：整弹 1 个 mode → 4 行同模式
新版：每行 1 个 mode → 4 行可不同
```

**推荐概率分配（默认配方）：**

| 行 | 默认模式 | 概率 | 理由 |
|----|---------|------|------|
| 第1行 | single | 高（如 70%） | 单人作为质量基本盘，保精选率下限 |
| 第2行 | single | 高（如 70%） | 同上 |
| 第3行 | duo | 中（如 25%） | 双人互动点缀，增加题材多样性 |
| 第4行 | duo 或 single | 按主题 | 弹性位：情侣主题弹可放 duo，日常弹放 single |

> 这只是**默认配方**，不是硬编码。AI 可以根据本弹主题（节日/情侣/日常）动态调整各行概率。

**`prep_state.json` 结构升级：**

```jsonc
{
  "episode": 55,
  "mode": "mixed",                    // 新增 mixed 模式（兼容旧 single/duo/quad）
  "row_modes": [                      // 4 行各自的模式
    {"row": 1, "mode": "single", "characters": ["星星布丁"]},
    {"row": 2, "mode": "single", "characters": ["星星布丁"]},
    {"row": 3, "mode": "duo", "characters": ["星星布丁","捞鱼"]},
    {"row": 4, "mode": "single", "characters": ["星星布丁"]}
  ],
  "row_linkages": [                   // 每行对应一组剧本（按行模式匹配）
    {"row": 1, "script_id": "...", "mode": "single"},
    {"row": 2, "script_id": "...", "mode": "single"},
    {"row": 3, "script_id": "...", "mode": "duo"},
    {"row": 4, "script_id": "...", "mode": "single"}
  ]
}
```

**生图流程改造：**
- `generate_from_prep_state.py` 按行生成：每行用该行 mode 对应的角色数和剧本
- 4 行分别用 4 组剧本（已有架构支持），现在再加上「每组剧本的模式标签」做匹配
- 剧本库 `linkage_scripts.json` 里每组剧本已有 `characters` 字段，天然可按单/双人筛选

**为什么不"整弹概率"而要"行级"？**
- 整弹概率（如 70% single 弹 / 30% duo 弹）：粒度太粗，一旦抽到 duo 整弹全废
- 行级概率：每弹都保证有一定比例的 single 行兜底，duo 行就算翻车也只影响 1/4

### 4.1 方案总览（三层优化）

```
第一层：策略层优化（改 SKILL.md 决策规则）    ← 见效最快，零开发成本
        核心：行级混合模式 + 概率倾斜 single
第二层：流程层优化（新增质量关卡）            ← 中等成本，质量提升显著
第三层：数据层优化（扩充参考图库+剧本库）      ← 持续投入，长期收益
```

### 4.2 第一层：策略层优化（修改 SKILL.md）

#### 改动 1：默认采用「行级混合模式」，single 概率倾斜

**现状**：`prep_episode.py --mode auto` 整弹选一个模式。

**优化**：新增 `--mode mixed`（推荐默认），在 `<creator-hard-rules>` 中新增铁律：

```markdown
11. 🔴 行级混合模式（质量与多样性平衡，默认采用）：
    不再整弹定一个 mode，而是 16 格 = 4 行故事，**每行独立选模式**。
    - 默认配方：2~3 行 single（高概率）+ 1~2 行 duo（中概率），single 倾斜
    - single 行作为「质量基本盘」：历史精选率 22.5%，保证每弹有兜底高分
    - duo 行作为「题材点缀」：历史精选率 8.5%，但提供互动乐趣（第12弹证明双人也能 81%）
    - quad 行：仅特殊节日合集用，日常不推荐（历史 0%）
    - AI 可根据本弹主题动态调整：情侣主题弹可多放 duo 行，日常弹以 single 为主
    - `prep_episode.py --mode auto` 默认输出 mixed；旧 single/duo 仍保留兼容
```

#### 改动 2：reference 模式优先策略（按行生效）

在 `<linkage-design-system>` 的生图流程部分，强化 reference 优先，且**按行判断**：

```markdown
**生图模式选择（按行，质量优先）：**
1. 每行先看参考图库：single 行匹配单人参考图，duo 行匹配双人参考图
2. 该行参考图充足 → 走 reference（精选率 37.5%）
3. 该行参考图不足 → 回退 ai_template，但 keyword 必须用短词 emotion_action 组合
4. reference 是 ai_template 的 3.7 倍精选率，应尽一切努力让更多行走 reference
```

#### 改动 3：服装选择约束

在 `<creator-flow-0-prep>` 准备模块新增：

```markdown
**服装质量分级（基于历史精选率）：**
- 推荐档：base5（22.7%）、base4（15.4%）
- 谨慎档：base6（3.7%）—— 使用前需视觉复核角色辨识度
- 禁用档：base3（0%）—— 除非有明确理由并记录在角色卡
```

### 4.3 第二层：流程层优化（新增质量关卡）

#### 改动 4：新增「含义命名质量校验」关卡

**问题**：当前 `check_and_rename.py` 只做识图命名，不校验命名的「聊天实用度」。

**方案**：在 `validate.py --stage post_generate` 新增含义词质量检查：

```python
# validate.py 新增检查项：meaning_chat_friendliness
def check_meaning_quality(meanings):
    """检查含义词是否符合聊天实用标准"""
    issues = []
    # 1. 字数：推荐 1-3 字，超过 4 字告警
    for w in meanings:
        if len(w) > 4:
            issues.append(f"'{w}' 超过4字，聊天中不易快速识别")
    # 2. 黑名单词：描述性/剧情化词
    desc_words = {'并肩坐','手拉手','靠着你','躺一起','悄悄话','惊讶对视',
                  '甜蜜抱','开心抱','害羞低头','冷战','全神贯注'}
    for w in meanings:
        if w in desc_words:
            issues.append(f"'{w}' 是描述性场景词，建议改成聊天反应词（如'抱抱'/'哇哦'）")
    return issues
```

#### 改动 5：新增「生图前 keyword 质量审核」

在 `<creator-flow-2-generate>` 生图模块，强制 keyword 风格校验：

```markdown
**生图前 keyword 审核（新增，强制）：**
执行 generate_from_prep_state.py 前，检查 keyword_combos：
1. ✅ 合格格式：`emotion_action`（如 `laughing_launching`、`crying_folded`）
2. ❌ 不合格格式：长描述句（如 "hugging with shy smiles"）
3. ❌ 不合格情绪：抽象文学词（floating/melting/starstruck/spaced out）
审核不通过 → 自动用 keywords.json 的 emotion_action_pairs 重新组合
```

#### 改动 6：duo 行专属加强复核（行级，非整弹）

在行级混合模式下，复核也按行做。duo 行在关卡1（生图后检查）新增强制项：

```markdown
**duo 行专属复核（新增，只针对 duo 行的 4 格）：**
双人行历史精选率仅 8.5%，生图后必须额外检查：
1. 两个角色是否都能清晰辨认（不是糊成一团）
2. 互动动作是否一眼能懂（不是需要解读的复杂剧情）
3. duo 行的 4 格至少 3 格达标「情绪可辨」
不达标 → 该行重生成，不影响其他 single 行
（行级混合的好处：duo 行翻车只影响 4 格，其余 12 格 single 行不受牵连）
```

### 4.4 第三层：数据层优化（长期建设）

#### 改动 7：扩充单人参考图库

**问题**：reference 模式质量最高，但只有 4 弹用过（第6-9弹），说明单人优质参考图库存量不足，导致后续 42 弹被迫降级到 ai_template。

**方案**：
1. 把精选目录的 138 张高质量表情，导入为新的参考图库（按情绪分类）
2. 建立 `reference_library/精选参考图/` 目录，按情绪标签组织
3. 目标：让 reference 模式成为可持续的默认模式，而非「早期才用得起」

#### 改动 8：linkage_scripts.json 剧本库按行模式标签化

**问题**：剧本库 174 组中，双人剧本（星星布丁+捞鱼）占 71 组（41%），单人剧本仅 47 组（27%）。行级混合模式下每弹要同时消费单/双人剧本，单人剧本库存明显不够。

**方案（适配行级混合）：**
1. **重点补充单人剧本**（当前 47 组 → 目标 ≥100 组），因为每弹的 single 行（2~3 行）消耗量大
2. **保留但优化双人剧本**：不淘汰双人剧本（行级混合需要它们做 duo 行），但给每组建一个 `quality_tier` 字段，优先选用历史高质量剧本
3. 每弹按 `row_modes` 从剧本库**按模式分别抽取**：
   - single 行 → 只从单人剧本池抽
   - duo 行 → 只从双人剧本池抽
4. 剧本库筛选函数新增 `by_mode` 参数，配合 `used_linkages.txt` 去重
5. 单人剧本要聚焦「聊天反应」场景：日常情绪、工作吐槽、社交回应（这是精选率高的命名风格）

#### 改动 9：建立质量反馈闭环（行级粒度）

**方案**：每弹发布后，人工标注精选图，**按行回写**质量数据，用于持续优化各行概率：

```python
# prep_state.json 新增字段
{
    "episode": 55,
    ...
    "row_modes": [
        {"row": 1, "mode": "single", ...},
        {"row": 2, "mode": "single", ...},
        {"row": 3, "mode": "duo", ...},
        {"row": 4, "mode": "single", ...}
    ],
    "quality_feedback": {
```

## 六、生产日志精细化方案（便于复盘分析）

### 6.1 当前日志的问题（复盘时发现的痛点）

这次分析 54 弹时，我深切体会到当前日志的局限——想做"为什么第14弹0%精选"的复盘，日志根本答不上来：

| 缺陷 | 现状 | 复盘影响 |
|------|------|---------|
| **无配置快照** | prep_state.json 有参数，但日志不汇总 | 想看"这弹用了什么配方"要翻多个文件 |
| **无质量信号** | 只记"OK/16张"，不记重试次数、识图置信度、透明度 | 看不出"顺利的一次生图"和"勉强凑齐的一次"的区别 |
| **含义词没入日志** | `_meaning_map.json` 存了16个原始命名，但日志只记"完成" | 想分析命名风格 vs 精选的关系，得逐个读 map 文件 |
| **无行级维度** | 整弹一个 mode，日志无行概念 | 行级混合上线后，日志完全没有行的视角 |
| **详细度随机** | 第9弹只有1条，第12弹全是空话，第14弹较详细 | 同样是"OK"，信息量天差地别 |
| **run_pipeline 塞空壳** | 第37/43弹日志是批量模板，非真实执行记录 | 不可信，无法据此判断真实质量 |

**根因**：`production_log.py` 的 `log_step()` 只接受 `details`(字符串) + `data`(dict) 两个自由字段，没有强制结构。各脚本想记什么就记什么，甚至用 `try/except: pass` 吞掉。

### 6.2 设计目标：让日志能回答复盘问题

一个好的生产日志，应该能直接回答用户复盘时会问的这些问题：

> - 这弹**配了什么**？（行模式、服装、keyword、参考图、剧本）
> - 生图**顺不顺利**？（重试几次、耗时、有没有格子失败重生成）
> - 命名**什么风格**？（16个含义词是什么、平均字数、有没有描述性词）
> - **哪行好哪行差**？（行级混合下，single 行和 duo 行各自表现）
> - **最后哪些入选精选**？（发布后回写，闭合复盘环）

### 6.3 方案：双文件结构（人类可读 + 机器可分析）

把日志从单一 `生产日志.md` 升级为 **`生产日志.md`（人读）+ `production_record.json`（机读）** 双轨制。

```
弹次目录/
├── 生产日志.md            ← 人类可读，保留现有格式（向后兼容）
├── production_record.json ← 新增！结构化全量记录，复盘用
├── prep_state.json        ← 制作前配置（已有）
└── 原图/_meaning_map.json ← 原始命名（已有，现纳入record）
```

### 6.4 改造 `production_log.py`（最小侵入）

现有 `log_step()` 保持兼容（老脚本不破），新增结构化 API：

```python
# production_log.py 新增（不改旧的 log_step）

def init_record(episode_dir, episode, config_snapshot):
    """准备阶段调用：初始化 production_record.json，写入配置快照。
    config_snapshot: 行模式、服装、keyword、参考图、剧本（一次写全）"""
    path = os.path.join(episode_dir, "production_record.json")
    record = {
        "episode": episode, "episode_name": os.path.basename(episode_dir),
        "created_at": _now(), "pipeline_version": "2.0",
        "config_snapshot": config_snapshot, "steps": {}, "quality_feedback": None
    }
    _write_json(path, record)

def log_step_rich(episode_dir, step, status, step_data, details="", duration_sec=None):
    """各阶段调用：把结构化 step_data 并入 record.steps[step]。
    step_data 是该步骤的完整结构化记录（见6.3的steps字段）。
    同时仍写一条 人读摘要 进 生产日志.md（向后兼容 validate.py 的检查）。"""
    path = os.path.join(episode_dir, "production_record.json")
    record = _read_json(path)
    entry = {"status": status, "ts": _now()}
    if duration_sec is not None: entry["duration_sec"] = duration_sec
    if details: entry["details"] = details
    entry.update(step_data)          # 合并结构化字段
    record["steps"][step] = entry
    _write_json(path, record)
    # 兼容：同步写一条人读摘要
    log_step(episode_dir, step, status, details, _summary_data(step_data))

def write_feedback(episode_dir, feedback):
    """发布后回写精选反馈。"""
    path = os.path.join(episode_dir, "production_record.json")
    record = _read_json(path)
    record["quality_feedback"] = feedback
    _write_json(path, record)
```

| 脚本 | 现在记什么 | 新增记什么（结构化） |

| `prep_episode.py` | "准备 OK" | `init_record()`：行模式、服装、keyword、keyword_style自动判定、参考图清单、剧本清单 |
