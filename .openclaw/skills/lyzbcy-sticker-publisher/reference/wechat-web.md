# 微信配套图、提审与原ID修复

## 现有publisher skill分支

先完成16张成品与视觉复核，再生成配套图、跑preflight、实际提交、按ID回读。用户仅要制作时到成品为止；要求发布或修复时沿已有授权完成必要提交，不重复索要普通许可。待审核/审核中不是审核通过，也不是已上架。

## 每弹专属配套图

使用 ../lyzbcy-sticker-creator/scripts/web_publish_assets.py，复用现有一键制作表情包的成熟横幅布局、正面大头封面及本弹赞赏图算法；脚本直接导入同仓库当前引擎；不调用生图模型。

命令：python ../lyzbcy-sticker-creator/scripts/web_publish_assets.py --episode-dir <本弹目录> --head-source <本弹纯头部正面素材> --banner-sources <本弹无字图1> <本弹无字图2> <本弹无字图3> --tip-source <本弹成品>。

- 每弹都重新渲染横幅750×400、封面240×240、图标50×50、赞赏引导939×701、赞赏致谢939×939；后两张在本弹「赞赏图」目录。不能用共享固定赞赏页作为静默回退，也不允许赞赏图生成失败后仍进入提交。
- 横幅只选本套当前角色、同服装/风格的现有无字素材，无变形。优先读取 header_sources.json、原图/_noword 或本弹已保存的参考图；不能通过排序文件名猜槽位。含短字的成品不直接作横幅源。缺素材先检查本地来源和裁切，不自动追加生图。
- 封面和图标走现有本地流程：优先已有 header_slots/header_sources.json 的真实来源，再选 _noword；仍缺时从本弹原图或同服装参考图裁出头部，经 make_big_head_cover 生成240封面，再将同一封面缩为50图标。不能缩整张全身图，也不能裁成残脸或带手道具。裁切参数和源SHA留档，实际查看头部完整性；不能把单张图的局部蒙版宣称成通用自动分割算法。禁止把“另生一张头像”当默认补救。609/610/612上轮确实追加过头像生图，用户已否定此默认做法，历史事实见仓库 docs/wechat-web-skill-pilot-20261105.md。
- 角色贴纸可以有白边；商店图标/封面另用无白边、透明底纯头部源。用成熟make_big_head_cover构图，图标与封面同图缩50像素；在真实50像素尺寸和放大图中都查看，不能只看存在或尺寸。
- 直接使用当前引擎的赞赏图渲染器，不复制字体/渲染实现。现行实现支持Windows微软雅黑/黑体；无字体时脚本阻断，不能提交无字卡片。跨平台字体支持应修主引擎后统一获得，不另养分支。
- 旧素材先备份；明确要替换时加 --replace。脚本在修复记录中保留旧图并写发布素材清单.json，记录真实来源和SHA256。生成完必须视觉核对每张图实际是本套人物。

## 分类和含义

分类依据真实角色，不只看含捞鱼标记：单人捞鱼→男人；单人星星布丁/周三涵/周五涵（当前角色定义）→女人；星星布丁＋捞鱼→人物合辑。新增角色先确认定义，不凭名字猜性别。平台采用二级菜单「人物角色→男人/女人/人物合辑」，选后读回完整文字。

含义词按实际每格画面核对。不能将一份计划按序写入另一张自由生成的图。示例：610曾将蹦跳标为在忙、点赞标为稍等；本轮逐格修正后保留原图，按原ID提审。

## 提交前检查

运行 python scripts/web_preflight.py --episode-dir <本弹目录> --role 女人（按实际角色换参数）。先实际看图，再写发布素材复核.json：approved=true、role、head_only=true、asset_hashes（对应当前发布素材清单files），以及审阅证据和来源；这是AI视觉复核，不得冒充用户评分或平台审核。任何素材重做后旧SHA审阅失效。

脚本检查数量、格式、尺寸、真实透明、重复哈希、介绍、本弹五项配套图、素材SHA与当前视觉复核的一致性；它不能自动证明头部/人物身份和图中文字正确，仍须Agent视觉检查。

## 真实网页操作

1. 登录本人微信表情开放平台，先读取完整名单，核对账号、名称、精确ID和状态。新投稿确认同名不存在；已有单修复只用原ID，不新建同名作品。
2. 新投稿：提交作品→表情专辑。先选静态、免费、下载全球、适当类型主题/风格；本轮612使用卡通/其他、人物角色女人、日常＋软萌可爱、情侣。保留当前上架地区；不擅自新增授权证明声明。
3. 先打开接受赞赏、填引导语，再传横幅/封面/图标/赞赏两图。每个槽单独上传，等待该槽正式缩略图src改变且图片加载；若裁剪弹框出现，点确定后再核对。fileCount=1或HTTP上传成功都不等于槽位接收成功。
4. 2026-11-05实际DOM：input.uploader__input在本编辑器依次为横幅、封面、图标、赞赏引导、赞赏致谢，共5个。首次仍先核对标签和槽位，不能永久假定索引；不包含原图/证明文件的WebUploader隐藏input。
5. 上传16张成品。等16个含义词输入框全部出现，逐个填词，核对图片与顺序、每格有值。只收到部分图片或平台拒绝重复图时停止，不残缺提审。
6. 隐藏radio/checkbox用可见label。每次选择后读checked；Vue同一次JS中连点多个checkbox可能只保留最后一项，本轮实测要补回日常，必须最终读回两项。不能用通用value=true混淆静态和免费。
7. 提交前记录当前表单、5槽mediaID、原图顺序/哈希和意向。新单可先保存草稿获得精确ID，再用只读草稿接口核对16张原始MD5及顺序；保存后按该ID继续提交，不重新新建。
8. 只点击一次提交。页面出现「表情提交成功，请耐心等待审核」，并按精确ID回读Status2/3、名称、16图、词义、角色分类和5项新媒体ID后，才记已提审。超时/未知先回读，不重复POST。最后再读一次全量名单确认无同名副本。

### 修复待审核旧单

先备份原平台草稿/素材、当前本地文件及SHA，并做好可审阅的新素材，再点「撤回编辑」→针对撤回提示点「确定」→确认已保存→精确「编辑」（不能模糊匹配撤回编辑）→替换必要槽位/词义→提交→按原ID回读。不能点击删除提示的确定。

编辑按钮可能使用window.open；普通合成click可能被浏览器拦截。此时用宿主真实点击，或在确认已保存且编辑入口存在后，进入已由当前平台验证的原ID编辑URL。Kimi宿主可用CDP焦点模拟＋真实鼠标事件，结束关闭焦点模拟；其他宿主用自己的浏览器点击能力。不要要求安装Kimi作为模块依赖。

## 已验证的只读接口（使用当前已登录页面fetch，禁止导出Cookie）

- 全量名单：GET /cgi-bin/mmemoticon-bin/home?lang=zh_CN&f=json；base_resp.ret=0，List含Name/StikerID/Status。最大编号要遍历完整List，兼顾待审/已保存，不只看第一页。本轮名单634→635，612只有一个精确ID。
- 原ID详情：GET /cgi-bin/mmemoticon-bin/stikerpage?stikerid=<ID>&f=json，验证StikerID与Status。
- 表单草稿：GET /cgi-bin/mmemoticonwebnode-bin/api/sticker/album/getStickerDraft?stickerId=<ID>，检查errCode、data.baseResp.ret、data.draft.stickerId/name/emojiList/stickerStyle和素材字段。
- 草稿字段：coverPicMediaId=横幅，mainIconMediaId=封面，panelIconMediaId=图标；rewardInfo.begPicMediaId/thanksPicMediaId=赞赏两图。名字容易误认，不能把mainIcon当50像素图标。
- clientContext.originalMd5可把平台emojiList的md5条目映射到上传原文件MD5；本轮612实测16/16一致。平台裁剪/压缩后媒体字节可能不同，不能拿成品SHA与平台小预览SHA硬比。

这些是当前实测字段。结构变更时保留现场，重新观察页面请求，不猜写入API参数。实际保存、撤回和提交继续使用平台自身表单；不把请求头/凭据或完整账号响应加入技能包。
