## 已知重点问题

### 1. 假透明背景

现象：
- 生成结果看起来像透明
- 实际图片没有 alpha 通道

结论：
- 不要把 `transparent background` 当成真透明方案
- 要靠 Chroma-key 或单图抠图

### 2. PowerShell 中文 prompt 乱码

现象：
- 中文 prompt 经 stdin pipe 后容易出问题

建议：
- prompt 尽量用英文
- 关键占位符和路径分开处理

### 3. 自动重命名不等于视觉理解

现象：
- 参考图名字和真实生成内容不一致

建议：
- 发布前必须做视觉复核

### 4. main.py 不应视为绝对可靠一键流

原因：
- 历史上出现过输出目录命名错位
- Codex 新图检测逻辑有过失效记录
- 文档承诺和脚本现实并不总是完全同步

### 5. 🔴 单故事撑16格必然注水（最重要的设计教训）

**现象：**
- 第19、20弹（单故事×16格模式）的含义词高度重复，16个里13个相同
- 第21弹初版「拆礼物」单故事展开后，第7-16格出现明显注水：好期待/忍不住啦/心跳加速/爱你哟/抱紧紧/最好啦，后4个实质都是"开心+爱"的换皮
- 用户反馈："感觉有些过于重复了，看来一个小故事只能支撑4-6张图"

**根因：**
- 旧架构 `expand_to_16_panels()` 把4格剧本硬展开成16格时，在锚点（panel 2/6/10/14）之间**硬编码了12个固定过渡词**（闲着没事/咦？/决定了！/全神贯注/累趴了/都过去了/今天也棒棒的…）
- 这些过渡词每弹都一样，且都是"等待区"凑数，没有独立笑点
- 本质问题：**一个微故事的剧情张力只能支撑4-6格**，强行拉到16格必然产生等待区和重复情绪

**结论（已固化为新架构）：**
- 一弹16宫格 = **4个独立小故事串联**，每行（4格）一个故事，行间独立
- 每个剧本标准就是 **4格**（起承转合），不再用 expand 展开
- 含义词来自4个不同剧本，题材天然多元，零重复
- 已验证：第21弹重生版（厨房甜蜜/咸鱼一天/看星星/春日野餐）16含义词全部独立、无重复

**这条经验已写入 SKILL.md 铁律10 + 联动设计系统，务必遵守。**

### 6. `--script` 参数的补足逻辑曾会覆盖指定剧本

**现象：**
- 给 `generate_from_prep_state.py` 加 `--script <id>` 指定优先剧本后，新模式选4个故事时，指定的剧本会被随机结果**覆盖掉**（没真正选中）

**根因：**
- `pick_linkage_scripts` 原逻辑：`if len(selected) < count: selected = available[:count]`，这行会**整体重置** selected，把 preferred 剧本丢掉

**修复：**
- 补足时改为排除已选中的 preferred：`remaining = [s for s in available if s.id not in chosen_ids]; selected = selected + remaining[:缺数]`
- 这样 preferred 必然包含，其余随机补足

**教训：**
- 给随机选择加"优先项"时，补足逻辑必须排除已选项，否则优先项形同虚设

### 7. 🔴 洋红 key 误抠红色/粉红衣服（chroma-key 材质坑，已修复）

**现象：**
- 第32、41弹「衣服染色」故事里，角色穿的**红色/粉红色衣服被抠成大片透明破洞**，视觉上像衣服缺失、脸破洞
- 同弹其他正常表情（无红色）不受影响

**根因（数据已验证，非猜测）：**
- 洋红 key `(255,0,255)` 在 `transparent_threshold=150` 下，会把所有满足 `R≥105 且 G≤150 且 B≥105` 的像素强制透明
- 红色/粉红衣服的色相 H≈335-340°（距洋红 H≈300° 仅 35-40°），落进了这个盒子
- config.yaml note 曾断言"粉肤色距洋红 ≥156，阈值 150 不会误伤"——**这个论据只测了肤色，没测红色衣服**。红衣服的通道距离正落在 86-150 的"洋红阴影区"

**为什么红衣和洋红在 RGB 上分不开、但在 HSV 上能分开（关键洞察）：**
| | 色相 H | 饱和度 S |
|---|---|---|
| 洋红背景/阴影 | ≈300° | **≈0.98**（纯色填充，极度饱和）|
| 黏土角色红/粉衣服 | ≈335°（距洋红仅35°）| **≈0.6**（哑光漫反射，饱和度天然低）|

色相上两者只差 35°（单 H 分不开），但**饱和度几乎不重叠（0.98 vs 0.6）**——这是材质本质差异：纯色填充必然高饱和，3D 黏土哑光材质无论什么颜色都会被漫反射+环境光拉低 S。

**修复（`remove_chroma_key.py` 加 hue-guard，默认开启）：**
```python
# 保护(不抠) 当且仅当：NOT ( 色相距300° ≤ 20°  AND  饱和度S ≥ 0.85 )
def _is_magenta_key(r, g, b):
    h, s, _ = colorsys.rgb_to_hsv(r/255, g/255, b/255)
    dh = min(abs(h*360 - 300), 360 - abs(h*360 - 300))  # 环形距离
    return dh <= 20 and s >= 0.85
```
- 在逐像素循环里，只有 `_is_magenta_key` 返回 True 的像素才进入抠图流程；明确非洋红的（红衣/肤色/其他色）强制保留
- CLI 开关 `--hue-guard`（默认开）/ `--no-hue-guard`（回退旧行为，用于 A/B 对比）
- 不改 `_dominance_alpha`/`_key_channel_dominance` 的数学（保持两个 gate 一致，避免失配）

**实测效果：**
- 红衣误伤率：32弹 23.34%→2.15%，41弹 16.09%→2.31%
- 真洋红残留：<25px（和修复前几乎无差别）
- 正常图回归：**额外丢失=0像素**，额外救回的全是正当前景（零退化）

**诊断方法（下次遇到类似"角色被抠空"先这样查）：**
```bash
cd .openclaw/skills/lyzbcy-sticker-creator/scripts
python rechroma_test.py --hue-guard --image "<源图路径>"
# 看"红衣误伤率"指标：高=被误抠，低=正常
```
- `rechroma_test.py` 的 `measure_misprotect()` 会区分"该留的前景被误抠"和"该抠的背景"
- ⚠️ 注意：旧 `stats()` 的"近洋红残留"用 RGB dominance 判定，会把保留下来的粉红衣服误报成残留；判断残留要用 HSV 判定（H300±20 且 S≥0.85）才是真洋红

**教训：**
- chroma-key 的色相冲突不能只靠 RGB 通道距离阈值——同类色（红 vs 洋红）在 RGB 必重叠
- HSV 双判据（H AND S）比单 H 或单 RGB 更稳，因为材质差异（饱和度）是物理本质
- 调全局阈值有回归风险时，优先加"材质保护短路"（明确非 key 的强制保留），而不是调阈值

### 8. 🔴 单人弹误选双人剧本（角色匹配过宽，已修复）

**现象：**
- 第37弹（单人星星布丁）生图后，图里出现**两个角色**（含捞鱼），且含义词重复（"看我的""糊了"各出现两次）

**根因：**
- `generate_from_prep_state.py` 的 `char_match` 用 `any(c in script_chars for c in characters)`
- 当 `characters=['星星布丁']` 时，**任何含星星布丁的剧本都匹配**，包括双人剧本（其 characters 标了 `['星星布丁','捞鱼']`）
- 单人弹于是选到双人剧本，prompt 生成"两个角色"，造成图与模式不符 + 含义词跨剧本重复

**修复（严格集合相等匹配）：**
```python
# 旧: return any(c in script_chars for c in characters)  # 过宽
# 新:
target = set(characters)
def char_match(s):
    script_chars = set(s.get("characters", []))
    if not script_chars:
        return False  # 严格模式不收通配剧本
    return script_chars == target  # 必须角色集合完全相等
```
- 单人弹 `[星星布丁]` 只匹配 characters 恰为 `['星星布丁']` 的剧本
- 双人弹 `[星星布丁,捞鱼]` 只匹配恰为这俩的剧本

**教训：**
- 角色匹配不能用 `any()`（子集命中过宽），必须用集合相等
- 单人剧本池（characters 标单一角色）不足时，要先补充单人剧本，不能靠"放宽匹配"凑数

## 故障排查

### 准备阶段失败

- 检查 `config.yaml`
- 检查 base 图路径
- 检查参考图库目录
- 检查参考图文件名是否符合规范

### 生图阶段失败

- 检查 Codex CLI 是否可调用
- 检查图片输入路径
- 检查是否误用了中文 prompt
- 检查单组是否需要单独重试
- **检查 Codex 网络连通性**（关键）：
  - 报错 `failed to refresh available models: timeout` 或 `stream disconnected` = 本机连不上 `chatgpt.com/backend-api`
  - 用 `curl -sS -o /dev/null -w "%{http_code}" https://chatgpt.com` 验证：返回 000/超时 = 网络不通
  - **根因通常是 VPN/代理没对终端生效**：系统代理（TUN模式/浏览器代理）不会自动传给 curl/codex
  - **解决**：在终端显式设置代理环境变量（Clash 默认端口 7890）：
    ```
    export http_proxy=http://127.0.0.1:7890
    export https_proxy=http://127.0.0.1:7890
    export all_proxy=socks5://127.0.0.1:7890
    ```
    探测端口：`for p in 7890 7897 1080 10808; do timeout 2 bash -c "echo>/dev/tcp/127.0.0.1/$p" && echo $p; done`
  - 代理生效后 chatgpt.com 会返回 403（正常，能连上即可），codex 即可生图

### 后处理失败

- 检查裁剪命令的 `--grid`
- 检查透明处理输出目录
- 检查命名是否重复

### 发布素材失败

- 横幅优先用更有张力的成品图
- 图标优先用脸部占比高的图
- 不要硬用自动拼图结果
