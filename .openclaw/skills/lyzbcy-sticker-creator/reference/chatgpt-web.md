# ChatGPT网页制作：原Sticker Maker分支

手绘动态GIF的一图多组实验，另读 [批量连续帧与防抖试制](gif-multisheet-trial.md)。本页后续固定16格静态制作/PNG投稿流程不直接套用于GIF。

只更新本仓库的现有creator/publisher skill和引擎，不安装独立网页包，不复制第二套素材/算法。概率与服装只读本skill config.yaml；单人85%、双人15%，单人条件星星布丁75%、捞鱼25%，双人为二者。

## 第一格固定方框头像

首次生图即约定第1格为正面头肩胸像，可独立发送；完整头发、脸与自然肩臂放在顶部居中80%方框内，文案只在底部92%—99%字幕带。双人时第一格两人并肩近景。其余15格只限定主题、场景、人群，让模型发挥，不强制故事。普通贴纸保留白描边。

头像始终取原始整图的第一格，坐标不按人物收紧、不重新居中：side=round(min(w,h)*0.8)，x=(w-side)//2，y=0。仅沿既有流程去洋红，再按方框裁剪和等比缩放；不抠字、不删白边、不做轮廓mask/连通域清理、不选其他格、不二次启发式裁头。240封面同图缩50图标。当前裁剪函数和像素保持测试在scripts/web_head_crop.py与test_web_head_crop.py。

如果生成未遵守预留区，记录失败，不暗改坐标、换格或擦字冒充成功。617/618首次中心80%仍带字幕，两弹已统一改为顶部居中80%；这是固定规则的全局修订，详见 [实测](../../../../docs/first-panel-avatar-20261105.md)。

## 用户指定高密度静态试验

用户2026-11-05要求精品优先，一张48格拆三弹；不是默认每次追求最多格数。一次整图只抽一次角色与服装，明确记录各弹共用master的抽样单位，不伪造独立抽样。仅框定每组主题、场景、人群，模型自主选词动作；首格约束分别作用于1、17、33（更多组以此类推）。同次JSON仍是候选，实际图决定文字和完整张数。

48格实测采用4列12行。长图可以只有724像素宽；完成判定须同时看短边至少256、长边至少800和生成图属性，不再要求宽度大于800。行高可能不等，不能整图等分12行。对已审完整原图，先为每弹准备空目录，再用 `python scripts/web_static_density.py --master <原图> --manifest <web_batch格式清单> --rows 12`。它复用当前沟位检测和web_process_grid.py，按每4行保存各弹原图、master SHA与全局格号，拒绝覆盖已有成品。随后沿用web_batch_local.py preliminary、视觉复核、assets和原publisher投稿。超过两弹的复核板按实际宽高合成，避免第三弹被裁出画布。

本次48格完整且632—634已真实提审待审核。64格只生成56张，80格虽然数量齐但变为扁长格、角色细节下降及字幕布局偏离，均记失败样本而未提审；这是本次观察，不代表模型绝对上限或48格已长期稳定。详细结果见[静态密度实测](../../../../docs/static-density-trial-20261105.md)。精品验收未通过的压力样本不当成正式发布数量；补生成须单列次数和耗时，不能仍称单图产出。

横幅来源已有透明alpha时，不再执行不透明背景去色。紧贴边界的自然头像可能让主体包围盒铺满画布，但不能据此把浅色脸和衣服当背景；634实测曾误伤，已在原make_banner.py修复并重渲染复核。

## 执行三个阶段

1. node scripts/web_batch.cjs begin --config <config.json>

config含outputRoot、assetsRoot、logDir、accountAnchor和1—10项themes（theme/scenario/audience），count须与themes数量一致，默认目标每弹150秒，可显式goalMs。从查号前开始计时。脚本读取本人后台完整List（含草稿待审）及已知账号作品ID，确定最大编号后用web_prepare.py抽样、复制实际base并记SHA。已有同名目录或未知结果先续接核验，不能覆盖/重生。微信标签关闭时自动打开官方入口，登录失效则停在登录状态，不导出Cookie。

通过ChatGPT真实附件输入上传base，确认加载后发送；按每组最多两弹分别新对话并行等待图像，组间顺序推进。首次响应同时要求16项index/text/meaning JSON，只作为候选，不能当图片真值。下载本次生成原图，保存聊天URL与SHA；脚本调用当前引擎切图/去底，自动生成首格头像和五项本弹配套图，按两弹一组输出review-groups/01..05/review-all.jpg，完成一组即写回manifest.reviewGroups。网页操作和生成细节见 [质量规范](chatgpt-web-quality.md)。

附件、文本与发送按钮必须属于同一个当前composer（会话页thread优先，否则home）；发送前核对该composer内参考缩略图数量等于base数量，且没有上传进度。不能仅凭upload返回success或页面任意发送按钮可用就发送：624实测曾因此只发出文字，ChatGPT明确要求补传附件。若明确未收到附件，保留原响应证据，在原会话补传并按上述条件核验后发送续接文字；结果未知时不重发。生成阶段中断后执行 `node scripts/web_batch.cjs resume --manifest <manifest.json>`，跳过已有reviewGroup、已有切图和已发送请求，继续读取原会话并推进尚未发送的弹；总时钟不重置。

2. Agent逐组在review-all.jpg核对32格身份、文字、切图边缘及两套五项配套图，可在下一组生成时复核已完成组，写review.json：albums内每项只有episode、16个meanings、description，不再填head_index/head_rect/polygon/caption_regions。然后执行 node scripts/web_batch.cjs assets --manifest <manifest.json> --review <review.json>。

此阶段规整词义标点（啊？→啊）、检测重复并更名，更新头像与素材来源路径；已审素材字节保持不变，无额外头像选图识图。发现实际质量问题仍需处理并计时，不能拿脚本尺寸检查冒充视觉合格。

切图恢复案例626：错误空带把中线识别到793（1254宽原图正常中线约627），造成混格。先把原成品、透明版、panels缓存和清单移入本弹.cache带时间戳备份，保留原图；再用同一web_process_grid.py加 `--fixed-grid` 调用现有引擎的等分归属＋完整连通域裁图。不能直接整格截取，跨格的手势/字幕会留下邻格碎片。恢复后重建该弹头像来源证明和配套（web_publish_assets.py --replace会备份旧配套），重新生成分组复核板、审查32格和10配套，再绑定新SHA。已有approved记录不得沿用。只在实际审图确认错误空带后启用，不全局替换默认内容感知切图。

3. 将当前发布素材清单SHA写入approval.json：逐弹episode、approved、portrait_reviewed、asset_hashes，human_score=null。node scripts/web_batch.cjs publish --manifest <manifest.json> --approval <approval.json>。

发布使用原 [publisher SDK分支](../../lyzbcy-sticker-publisher/reference/wechat-web.md)：4并发上传、创建/保存/提审前宿主原子日志ACK、32张原始MD5/词义/顺序及五项配套ID校验、每弹仅提交一次，最后按精确ID及全量同名唯一性回读。每两弹在publish-groups下独立保存sdk-journal.json和回执，主目录partial-receipts.json逐组落盘；已有日志拒绝重放，超时/未知先核销。不可把上传、保存、待审核当审核通过或上架。

## 来源与计时

后处理、赞赏图和横幅继续调用同仓库当前引擎及现有脚本，禁止携带复制快照；本弹配套图每弹本地重渲染，不复用共享赞赏页。头像必须来自当弹第一格，不能复用base或其他弹。

全程从首次启动到最终回读，保留登录恢复、失败、补救、审阅和Agent编排等待。另报连续生产用时可以，但不得替代总时长。617/618完整6分31秒；含首次入口失败与补救93秒，恢复后生产4分58秒，SDK29秒。首次头像参数全局修订及一次额外方框验证也在日志内；不保证外部生图耗时。

## 10弹扩量与计时

617/618证明第一格预留＋顶部80%取景可省去头像选图与抠字。扩量保持该规则，只扩count，禁止写死做两弹后冒充完成。默认每组2弹生成，完成即输出审图板供Agent复核；候选含义来自同次响应且索引须完整1—16，仍由实际图复核，不能直接信任。生成结束后一次应用全部审核过的含义，SDK按2弹一组顺序提交并持久化回执。

10弹目标按已确认的2弹约5分钟线性设为25分钟；计时从首次查号到最后10套唯一名称回读，包括所有失败与等待，不把准备补救从总时间中扣掉。发布成功、待审核、审核通过、上架分别记录。所有脚本与资料仍只维护在原仓库，不复制独立包。

619—628首次十弹实测：查号前启动至最后提审核验22分31.422秒（含624漏附件及626错误空带补救），SDK十弹共144.246秒，10弹均真实提审待审核、每弹仅提交一次；随后全量List复核十名称唯一且ID一致。正常生图56.688—120.350秒，未稳定达到1分钟；分组复核延迟也非全部小于1分钟，不能用总目标达成冒充全部子目标达成。开发与事后沉淀另计，完整口径、故障与验证见 [十弹实测](../../../../docs/ten-album-web-trial-20261105.md)。
