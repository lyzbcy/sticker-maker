# 软件对应开发 Skill（规范）

## 目的

如果让不同的 Agent 去接管一个软件的开发，新 Agent 会去检索上下文，但对这个项目的把控度没有原来的好——冷启动成本高、容易破坏既有约定。

因此规定：**每一个正式维护的软件，在其开发目录下必须有一个对应的开发 Skill**。任何 Agent（或人）接手时，第一件事就是读这个 Skill，按它指的路快速进入状态，而不是全量翻代码猜上下文。

## 一、目录结构标准

软件的开发目录按下面的骨架组织（没有的模块允许缺省，但不允许另起炉灶）：

```
<软件根目录>/
├── SKILL.md              ← 开发入口，任何接手者从这里开始
├── docs/                 ← 项目知识库（渐进式披露的中枢）
│   ├── agent.md          ← docs 的入口与导航（目录管理）
│   ├── roadmap.md        ← To-do list / 开发情况 / 已完成里程碑
│   ├── tech.md           ← 技术方案（架构、选型、关键决策及原因）
│   └── <模块名>.md        ← 按模块拆分的设计文档（如 login.md、updater.md）
├── reference/            ← 供渐进式披露的深度资料（源码解读、踩坑记录、接口细节）
│   └── <模块名>/
└── src/ ...              ← 实际代码
```

**渐进式披露原则**：SKILL.md 只放"地图"不放"地图上的每一栋楼"。Agent 要开发某块功能时，由 SKILL.md 指到 docs/<模块名>.md；需要更深细节时，再由该文档指到 reference/<模块名>/ 下的资料。层层深入，按需读取，节省上下文。

## 二、SKILL.md 必含内容（缺一不可）

1. **项目一句话**：这个软件是干什么的、给谁用的。
2. **技术栈**：语言、框架、构建方式、运行环境。
3. **目录地图**：根目录下每个文件夹/关键文件是干什么的。
4. **docs 索引**：指向 docs/agent.md，并注明"开发任何功能前先查对应模块文档"。
5. **开发约定**：命名规范、分支规范、提交规范、日志规范（对接《日志系统.md》）。
6. **版本号规则**：当前版本号在哪个文件维护；每次开发完成后必须更新版本号并同步远端（对接《自适应更新检测.md》）。
7. **红线**：不许动的文件/配置、破坏了会怎样的警告（如自动更新逻辑、签名配置）。
8. **功能现状与验收入口**：列出关键要求的实现状态、对应代码/文档、验证命令或报告；未实现项明确写出。版本检查、自动更新、日志及启动器适配按实际适用范围逐项核对，不能仅因引用了规范就写“已完成”。

## 三、docs 管理规范

1. `docs/agent.md` 是唯一导航入口：列出 docs 下每份文档的主题和"什么情况下该读它"。
2. 文档按**模块**拆分，一个模块一份；超过 300 行就该拆。
3. **文档与代码同生命周期**：改了设计必须同步改文档，文档过期比没有文档更害人——Agent 会按错的来。
4. 每份模块文档头部放三行摘要：现状（稳定/重构中/废弃）、负责人、最后更新时间。

## 四、版本号与自适应更新联动

按《自适应更新检测.md》执行，Skill 中必须写明的硬规则：

- 开发完成 = 代码 + 文档 + **版本号** 三者同步更新，缺一不算完成。
- 版本号更新后必须按项目约定推送远端；正式发版还要发布对应包与更新元数据。Git 提交或版本号变化本身不会自动让客户端发现新版。
- 核对客户端是否真的实现“读取本地版本 → 查询远端正式版本 → 比较 → 提醒”。软件目录最新发布查询、本机已安装识别、软件自身更新，分别记录各自状态；不能用其中一项代替另一项。
- 更新模块文档应说明：每日检查口径、手动重试、下载校验、安装与重启、失败回退，以及旧客户端首次迁移方式。具体要求见《自适应更新检测.md》。
- 涉及更新器自身的改动，属于红线级别，必须在 docs 中单独记录原因与测试结论。

## 五、新 Agent 接管自检清单

接手任何软件时，按顺序执行：

- [ ] 读 SKILL.md 全文（5 分钟内应能答出：软件是什么、技术栈、目录结构）
- [ ] 读 docs/agent.md 与 roadmap.md，确认当前进度和下一步
- [ ] 找到将要开发的模块文档，通读；需要更深细节再进 reference/
- [ ] 确认版本号当前位置与当前值
- [ ] 核对功能现状和验证入口；先查代码与验收证据，再判断哪些规范已落实
- [ ] 开工前复述一遍"我要改什么、会碰哪些红线"再动手

## 六、可复制的 SKILL.md 模板

````markdown
---
name: <软件名>-dev
description: <软件名>的开发技能。当用户要开发、修改、排障、更新该软件时使用。
---

# <软件名> 开发 Skill

## 项目一句话
<一句话：做什么的、给谁用>

## 技术栈
<语言/框架/构建/运行环境>

## 目录地图
- SKILL.md — 本文件
- docs/ — 知识库（先读 agent.md）
- reference/ — 深度资料（按需读）
- src/ — 源码
<逐项补充>

## 开发流程（任何 Agent 必须遵守）
1. 开发任何功能前，先读 docs/ 下对应模块文档；没有就先建。
2. 改动完成后：更新代码 + 更新模块文档 + 更新版本号（位置：<文件与字段>）+ 推送远端。
3. 日志按《日志系统.md》规范输出。
4. 发版时按《自适应更新检测.md》核对真实更新链路；桌面软件接入捞鱼软件中心时读取启动器适配 Skill 并运行严格自查。记录尚未实现或尚未验收的项目。

## 功能现状与验证入口
- 自身版本检查/更新：<已实现/部分实现/未实现；对应代码、docs/updater.md、验证命令或报告>
- 启动器适配：<适用情况、稳定产品 ID、主程序名；适配描述文件与自查入口>
- 测试/实际验收：<命令与报告位置；注明哪些步骤只做过模拟>
- 未完成项：<具体缺口；没有证据的功能不能写已完成>

## 红线
- <不许动的文件/配置及原因>

## 当前状态
- 版本：<x.y.z> ｜ 进度详见 docs/roadmap.md
````

## 七、与其他组件的关系

- 《启动器适配/接入指南.md》：桌面软件接入捞鱼软件中心时，读取 `E:\共享\tools\软件开发\启动器适配\laoyu-launcher-adapter\SKILL.md`；在项目根目录维护 launcher-adapter.json，发布前运行严格自查，并在项目 Skill 与 docs/agent.md 中添加入口。包检查通过不代替启动器登记、实际安装和运行验收。
- 《日志系统.md》：开发约定中的日志规范来源。
- 《自适应更新检测.md》：版本号规则与更新器设计来源。
- 《skill 组件/skill 静默更新.md》：本 Skill 自身（作为文件）被静默更新的机制。
